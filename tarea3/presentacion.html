El problema: condición de carrera

Dos taquillas venden el mismo asiento (0,0):

Taquilla A

Consulta (0,0) → libre

Vende (0,0)

Taquilla B

Consulta (0,0) → libre

Vende (0,0)

Resultado: el asiento se vende dos veces. Varios hilos accedieron al recurso compartido sin coordinarse.

std::thread — crear y esperar hilos

#include <thread> Un hilo es un flujo de ejecución dentro del proceso que comparte memoria con los demás.

#include <thread> // cabecera de std::thread void tarea() { /* trabajo del hilo */ } std::thread hilo(tarea); // crear el hilo hilo.join(); // esperar a que termine // hilo.detach(); // o separarlo (fondo) if (hilo.joinable()) { /* sigue siendo join/detach-able */ }

join() vs detach()

  • join(): el principal espera al hilo. Opción segura.
  • detach(): el hilo corre en segundo plano. Riesgoso si el main termina antes.
  • joinable(): true si aún se puede hacer join/detach.

Regla práctica: preferir join() y reservar detach() para tareas de fondo.

std::mutex — exclusión mutua

#include <mutex> Es como la puerta de un baño: solo un hilo entra a la vez.

#include <mutex> std::mutex mtx; // protege el recurso compartido mtx.lock(); // entra; si está ocupado, ESPERA // ---- región crítica ---- mtx.unlock(); // sale y deja pasar al siguiente if (mtx.try_lock()) { // no bloquea: devuelve bool /* región crítica */ mtx.unlock(); } else { /* estaba ocupado: hago otra cosa */ }

Funciones

  • lock(): adquiere; se bloquea si está ocupado.
  • unlock(): libera. ¡Siempre debe llamarse!
  • try_lock(): intenta sin esperar; devuelve bool.

Cuidado

Olvidar unlock() o salir por return/excepción → deadlock.

Variantes: recursive_mutex (re-bloqueo del mismo hilo) y timed_mutex (try_lock_for / try_lock_until).

RAII: el unlock() automático

#include <mutex> Un objeto adquiere el recurso al construirse y lo libera al destruirse.

Herramienta Bloquea al crear Se libera Cuándo usarla
lock_guard Sí Al salir del bloque Caso simple y rápido
unique_lock Configurable Al salir del bloque Cuando se necesita flexibilidad
scoped_lock Sí (varios) Al salir del bloque Varios mutex a la vez

Sintaxis RAII — lock_guard y unique_lock

#include <mutex>

// lock_guard: simple y rápido { std::lock_guard<std::mutex> lock(mtx); /* región crítica */ } // destructor → unlock() automático // unique_lock: flexible y movible std::unique_lock<std::mutex> lock(mtx, std::defer_lock); lock.lock(); // bloqueo cuando yo quiera lock.unlock(); // y libero manualmente si hace falta // varios mutex a la vez, sin deadlock std::scoped_lock lock(mtxA, mtxB);

Estrategias de unique_lock

  • defer_lock: no bloquea al construir.
  • try_to_lock: intenta sin esperar; revisar owns_lock().
  • adopt_lock: el mutex ya está bloqueado.

Ventaja

El unlock() ocurre aunque haya return o una excepción.

El problema del cine

Sala de 8 × 10. Al asignar un asiento se registra nombre y edad.

Operaciones

  • Asignar asiento (solo si está libre)
  • Liberar asiento
  • Buscar por asiento / por nombre
  • Mostrar la sala

Regla de oro

Proteger con el mismo mutex todas las lecturas y escrituras del recurso compartido.

Si solo se protegen las escrituras, la carrera continúa.

Énfasis

Grafo de precedencia

Quién debe esperar a quién antes de avanzar

Grafo de precedencia

Las flechas son precedencias: quién debe ocurrir antes.

¿Cómo se lee el grafo?

  • Inicio → Clientes: tras inicializar la sala y el mutex, los clientes se lanzan en paralelo.
  • Clientes → Región crítica: todos deben pasar uno a uno por el mutex. Esa restricción serializa el acceso.
  • Región crítica → Join: la sincronización no termina hasta que cada hilo libera el mutex.
  • Join → Consolidación: mostrar y buscar solo ocurren cuando todos los hilos terminaron.

Resumen: paralelismo en los clientes, serialización en la región crítica, barrera en el join.

Énfasis

Bloques COBEGIN–COEND

Todo lo que está entre ellos se ejecuta en paralelo

La notación COBEGIN–COEND

// inicialización secuencial (FUERA del COBEGIN) inicializar sala 8 × 10 y su mutex COBEGIN P1 : reservar(Ana, 0, 0) // compiten por (0,0) P2 : reservar(Luis, 0, 0) // compiten por (0,0) P3 : reservar(María, 0, 0) // compiten por (0,0) P4 : reservar(Pedro, 2, 4) P5 : reservar(Sofía, 3, 7) COEND // fase secuencial posterior (tras COEND) liberar (2,4) buscar por asiento (0,0) buscar por nombre "Sofía" mostrar la sala

Lectura

  • Fuera del bloque → ejecución secuencial.
  • Dentro → todas las tareas en paralelo.
  • COBEGIN marca el inicio del paralelismo.
  • COEND marca la barrera: se espera a que todas terminen.

COBEGIN–COEND y exclusión mutua

P1, P2 y P3 atacan el mismo asiento (0,0) al mismo tiempo:

Sin mutex

El asiento se vende varias veces.

Condición de carrera.

Con mutex

Solo uno gana.

Los demás reciben “no disponible”.

El bloque paralelo se comporta igual de rápido, pero el mutex garantiza el resultado: Ganador: Ana → (0,0); Luis y María rechazados.

Conclusiones y buenas prácticas

  • Los hilos comparten memoria: hay que sincronizarlos.
  • join() espera; detach() separa (usar con mucho cuidado).
  • El mutex protege la región crítica.
  • RAII (lock_guard, unique_lock, scoped_lock) libera el recurso solo.
  • Grafo de precedencia: define el orden; COBEGIN–COEND: define el paralelismo.
  • Proteger con el mismo mutex todas las lecturas y escrituras.
